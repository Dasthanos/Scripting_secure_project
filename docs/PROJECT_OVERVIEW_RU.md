# SecureGuard — краткое объяснение проекта

## Что делает программа

SecureGuard — учебный сканер безопасности исходного кода. Ему нужно передать конкретный файл или папку с проектом. Он читает файлы Python и C/C++, ищет некоторые известные опасные конструкции и сохраняет отчёты. Он не проверяет весь компьютер и не запускает найденный код.

У программы три этапа анализа:

1. **Статический анализ** ищет заданные шаблоны и простые потоки данных: например, пользовательский ввод, дошедший до `eval()` или shell-команды.
2. **Локальный RAG** ищет пояснения CWE, примеры и безопасные варианты в JSON/JSONL-базах. Он понимает поля SecureGuard (`title/description/unsafe/safe`) и распространённые поля MITRE (`name/desc/bad/good/lang/cves`). Поиск учитывает язык исходного файла и берёт не больше одной записи на CWE. Для уже найденной статическим анализом проблемы сначала ищется точный CWE; его описание и способ исправления попадают в отчёт и контекст для модели. Это поиск по готовой базе, а не обучение модели.
3. **Ollama** по желанию просматривает исходный код и материалы RAG. Затем проверка доказательств сверяет цитату с настоящим кодом: допускается целая строка или достаточно длинный точный фрагмент. Если такой фрагмент встречается только в одной строке, программа может исправить неверный номер строки. В отчёт попадают только прошедшие эту проверку находки.

Всё выполняется на компьютере. Проект разрешает подключение Ollama только через `localhost` или loopback-адрес.

## Демонстрация на включённых примерах

Из папки проекта выполни:

```bash
python3 secure_audit.py --demo --model qwen2.5-coder:3b --out demo_output
```

Папка `samples/` содержит четыре учебных файла:

- `safe_app.py` и `safe_app.c` показывают более безопасные примеры;
- `vulnerable_app.py` и `vulnerable_app.c` специально содержат уязвимые примеры.

В Python-демо также есть пары примеров для безопасной загрузки YAML, проверки TLS-сертификатов и создания временного файла.

Поэтому найденные в `vulnerable_*` проблемы заранее заложены авторами примеров. Этот запуск показывает работу программы на демонстрационных данных, а не проверяет отдельный проект пользователя и не доказывает обнаружение неизвестных уязвимостей.

Если нужна демонстрация без Ollama:

```bash
python3 secure_audit.py --demo --no-llm --out demo_output
```

## Проверка собственного кода

Подставь путь к своему файлу или каталогу вместо примера:

```bash
python3 secure_audit.py /полный/путь/к/файлу.py --model qwen2.5-coder:3b --out my_report
```

Чтобы проверить папку проекта:

```bash
python3 secure_audit.py /полный/путь/к/проекту --model qwen2.5-coder:3b --out my_report
```

Сканер сейчас принимает `.py`, `.c`, `.h`, `.cc`, `.cpp`, `.cxx`, `.hpp` и `.hxx`. В Python дополнительно проверяются явное отключение TLS-проверки, `tempfile.mktemp()` и небезопасные YAML-загрузчики. Если в указанной папке поддерживаемых файлов нет, программа сообщит об этом.

## Подключить большую базу CWE

Скопируй файл одногруппников, например `rag/kb.jsonl`, в `secureguard/knowledge_base_full.jsonl`. Затем подключи обе базы, чтобы сохранить и наши короткие заметки:

```bash
python3 secure_audit.py --demo --model qwen2.5-coder:3b \\
  --kb secureguard/knowledge_base.jsonl secureguard/knowledge_base_full.jsonl \\
  --out demo_output
```

Можно указать несколько файлов, например `kb.jsonl`, `seed_kb.jsonl` и `cve_seed.jsonl`. Загрузчик принимает JSONL (по одному JSON-объекту в строке), JSON-массив и JSON-объект с массивом записей. Языковые примеры, не относящиеся к Python/C/C++, не попадут в поиск по этим файлам; общие CWE-записи останутся доступны.

## Где результаты

В указанной после `--out` папке появятся:

- `report.md` — отчёт, который удобно открыть и читать;
- `findings.json` — те же находки в структурированном JSON;
- `findings.sarif` — формат для инструментов анализа кода, поддерживающих SARIF;
- `run.json` — параметры и статистика запуска, включая предложения модели и результаты проверки доказательств.

В отчёте:

- **Model proposals** — сколько находок предложил Ollama;
- **Accepted by evidence gate** — сколько предложений прошло проверку точного совпадения с исходным кодом;
- **Unique model-only findings added** — сколько из них добавилось к статическим находкам как новые;
- **Model findings matching static findings** — сколько принятых предложений уже было найдено статическим анализатором;
- **Rejected by evidence gate** — сколько предложений не прошло проверку, с причинами.

По умолчанию RAG использует BM25 и не требует дополнительной модели. Для локального семантического поиска можно указать отдельную установленную embedding-модель Ollama через `--embedding-model`. Индекс строится заново при каждом запуске и может занять время. Например:

```bash
ollama pull all-minilm
python3 secure_audit.py --demo --no-llm --embedding-model all-minilm --out demo_embedding
```

Если статический анализ помечает строку как возможный секрет, отчёты скрывают текст этой строки заменой на `[REDACTED]`.

Если новых модельных находок ноль, это не обязательно означает ошибку соединения: возможно, модель ничего не предложила, её цитата не совпала с исходным кодом или она повторила статическую находку. В отчёте также отмечено, какие CWE удалось точно сопоставить с базой. CVE, перечисленные в записи CWE, являются примерами, а не подтверждением уязвимости конкретного проекта или его зависимостей.

## Ограничения

Это учебный прототип, а не доказательство безопасности. Python-анализ использует ограниченный разбор AST и простое отслеживание данных. C/C++-анализатор лексический, не компиляторный. Возможны пропуски и ложные срабатывания. Чистый отчёт не доказывает отсутствие уязвимостей. Ранее показанный запуск дал 11 находок до добавления новых Python-примеров; текущий результат следует посмотреть повторным запуском демо. Результаты собственной программы нужно разбирать отдельно.
